# Oído Cocina — Agent Guide

Backend API for restaurant management: menu and dishes, tables and reservations, users and
permissions, per-restaurant settings, staff and opening hours. **FastAPI + PostgreSQL**,
multi-restaurant from the ground up. Domain language, API error messages, seed data and the
README are in Spanish; code, identifiers and docstrings are mostly in English.

Current state: Sprint 1. The database layer (versioned migrations + idempotent seeders) is the
solid part. The API is only a skeleton (`/api/v1/health`) and identity/permissions are temporary
development stubs.

## Commands

Run everything from the repository root (where `alembic.ini` lives).

```powershell
env\Scripts\activate                  # Windows (the checked-out virtualenv is `env/`, not `.venv/`)
source env/bin/activate               # Linux / macOS
pip install -r requirements.txt

alembic upgrade head                  # create/update the schema
python -m app.database.seeders        # idempotent demo data (check output: "0 inserted" on re-run)
uvicorn app.main:app --reload         # serve at http://127.0.0.1:8000/api/v1/health
python -m pytest                      # full suite
python -m pytest tests/database/test_seeders_idempotency.py::test_second_run_does_not_modify_existing_rows -q
```

If the shell is not activated, use `env\Scripts\python.exe -m pytest` / `env\Scripts\alembic.exe`.
There is no linter/formatter configuration in the repo; keep style consistent with surrounding files.

## Setup and tests

- Copy `.env.example` to `.env` and fill it in. `.env` is gitignored and must never be committed.
- `DATABASE_URL` is mandatory (`postgresql+psycopg://user:password@localhost:5432/oido_cocina`).
  Alembic reads the URL from this variable, **not** from `alembic.ini`.
- Tests run against the configured PostgreSQL database and roll back after each test.
  They expect a local database: some tests assert the host is `localhost`/`127.0.0.1`.
- Missing `DATABASE_URL` makes DB tests skip; a configured-but-unmigrated DB fails loudly.
  Run `alembic upgrade head` before testing.
- `SEED_DEMO_PASSWORD` is required when demo users must be created; the seeder aborts without it.

## Architecture

Request flow: `app/api/` (routers) → `app/controllers/` (logic) → `app/schemas/` (Pydantic models).
`app/main.py` builds the app, registers the common exception handlers and mounts routers under
`settings.api_prefix` (`/api/v1`).

- `app/core/config.py` — cached `get_settings()` (pydantic-settings, reads `.env`).
- `app/core/database_connection.py` — cached engine/session factory and the `get_db` dependency.
- `app/core/security.py` — the single place for password hashing (`hash_password` / `verify_password`, Argon2id).
- `app/core/errors/` — the one error system: `ErrorCode`, `AppError` subclasses, handlers and response schema.
- `app/core/kernel/` — **temporary** dev identity and permission stubs (`AUTH_STUBS_ENABLED`).
  Removed by HU-AUT-04/HU-AUT-05. `app/core/kernel/errors.py` is a stale duplicate: use `app/core/errors/`.
- `app/database/base.py` — the single declarative `Base`, naming convention and `TimestampMixin`.
- `app/database/migrations/` — the single Alembic history (environment + versions).
- `app/database/seeders/` — demo data; `runner.run_all()` runs them in dependency order.
- `app/models/__init__.py` — re-exports every model and is what Alembic imports.
- `app/models/` and `app/modules/<module>/models/` — current model locations (`users`, `dishes`, `settings`).

**One `Base`, one Alembic history.** Never create another `alembic/` directory or another
declarative base: two histories over the same database block each other.

## Conventions

- `snake_case` everywhere; tables are plural. `created_at` / `updated_at` come from `TimestampMixin`
  (timezone-aware). `audit_logs` is append-only and has only `created_at`.
- Constraint names are deterministic (`pk_`, `fk_`, `uq_`, `ck_`, `ix_`) via the naming convention in
  `app/database/base.py`, so migrations stay stable and downgrades can drop by name.
- Soft delete with `is_active`; do not hard-delete business rows.
- Restaurant-scoped data must carry `restaurant_id`. `users.restaurant_id` is nullable only for
  superadmins and customers, who do not belong to a single restaurant.
- No business configuration hardcoded in code: courtesy time, slot length, breaks and opening hours
  live in `restaurant_settings` / `opening_hours`.
- Every model must be imported in `app/models/__init__.py` or Alembic will not see it.

### Migrations

All schema changes go through a versioned migration, never by hand:

```powershell
alembic revision --autogenerate -m "short description"
alembic upgrade head
alembic check          # models and database agree
alembic downgrade base # prove the down path
```

Always review autogenerated files and test the `downgrade`; autogenerate can miss server defaults,
type changes and constraint details.

### Seeders

- Use `insert_if_missing(session, Model, rows, natural_key=[...])` so re-runs insert `0` rows.
- Use stable natural keys (allergen `code`, role `name`, user `email`, `restaurant_id + name`, ...).
- Never update or re-hash existing rows. Missing secrets raise `SeedError` and abort the transaction.
- `run_all()` does not commit; the caller owns the transaction (see `app/database/seeders/__main__.py`).

### Errors and privacy

- Raise `AppError` subclasses (or plain `HTTPException`) and register codes in `ErrorCode`.
  Clients always receive `{"error": {"code": "...", "message": "..."}}`; user-facing messages are Spanish.
- Never leak SQL, hostnames, stack traces or internal details in a response. Log the trace server-side.
- Do not add a second error-handling layer; extend `app/core/errors/`.

## Gotchas

- `app/api/test_routes.py`, `app/controllers/test_controller.py`, `app/schemas/test_schema.py` and
  `app/models/test_model.py` are **production modules** with a misleading `test_` prefix.
  `pytest.ini` sets `testpaths = tests`, so pytest does not collect them — keep it that way.
- The working tree has shown in-progress merge artifacts (duplicate definitions). If collection fails with
  `could not assemble any primary key columns for mapped table 'restaurant'` or
  `declarative base already contains a class with the same class name`, look for duplicate class
  definitions in `app/modules/settings/models/restaurant.py` before changing anything else.
- Some older tests are stale relative to the current API (e.g. importing `engine` from
  `database_connection`, or using `time_zone` instead of `timezone`). Fix the test to use
  `get_engine()` / the current model rather than adding compatibility aliases.
- The demo `min_break_between_shifts = 720` minutes is sample data pending validation against the
  applicable labour agreement; do not treat it as a business rule.
